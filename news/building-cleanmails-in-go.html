An open, self-hosted cold email platform with MCP support

How we built a full email sending infrastructure in Go using Gin, Asynq, and GORM. Covers the dispatcher, the MCP layer, parallel validation, the spintax engine, and why we chose this stack over Node/Python.

[ Architecture diagram: API + Worker + Redis + Postgres + Next.js ]

I've been running cold email campaigns for agency clients for about two years now. Instantly, Smartlead, Lemlist, all of them. They all work fine until you hit 20+ clients and your monthly bill is over $2k for software that's basically a CRUD app, a scheduler, and some SMTP connections.

So I built my own. It took about 4 months of actual coding, runs on a single $20 VPS, handles all my clients, and I recently open sourced most of the engineering behind it. This post is about the technical decisions, not the product. If you want to look at the architecture and tell me I'm wrong about something, that's what I'm here for.

Stack overview

The system is two Go binaries (API server + background worker) talking to Postgres and Redis. Frontend is Next.js but that's just a dashboard, the interesting stuff is all backend.

  • Go 1.25 with Gin for HTTP routing
  • GORM for database (I know, I know. But migrations work and it's fast enough for this workload)
  • Asynq (Redis based task queue) for all background work
  • Postgres 16 for everything persistent
  • Redis 7 for task queue + caching

The API binary handles HTTP requests, the worker binary processes background jobs (sending emails, validation, warmup cycles, IMAP sync, webhook dispatch). They share the same codebase under internal/ but compile to separate binaries.

The dispatcher: sending emails without looking like a bot

This is probably the most interesting piece. The dispatcher runs every 60 seconds as a scheduled Asynq task. It finds leads that are "due" for their next email and sends them, but with a bunch of constraints that make it behave like a human typing emails one by one.

func (p *CampaignDispatcherProcessor) ProcessTask(ctx context.Context, t *asynq.Task) error {
    // Use FOR UPDATE SKIP LOCKED to prevent race conditions
    // between overlapping dispatch cycles
    var leads []models.Lead
    
    err := p.DB.Raw(`
        SELECT * FROM leads
        WHERE next_send_at <= ?
          AND is_blocklisted = false
          AND status NOT IN (?, ?, ?)
        ORDER BY next_send_at ASC
        LIMIT 50
        FOR UPDATE SKIP LOCKED`,
        now,
        models.LeadStatusBounced, 
        models.LeadStatusUnsubscribed, 
        models.LeadStatusReplied,
    ).Scan(&leads).Error
    
    for _, lead := range leads {
        p.processLead(ctx, &lead, now)
        
        // Human-mimicry delay: 30-90 seconds between sends
        delay := time.Duration(30+rand.Intn(60)) * time.Second
        select {
        case <-ctx.Done():
            return nil
        case <-time.After(delay):
        }
    }
    return nil
}

The FOR UPDATE SKIP LOCKED bit is important. If a previous dispatch cycle is still running when the next one fires (because sending 50 emails with 30-90s delays takes 25+ minutes), the new cycle doesn't get stuck waiting for a row lock. It just grabs whatever leads aren't already being processed. Postgres handles this natively and it's way more reliable than any application level locking I could build with Redis.

Each send goes through: mailbox selection (round robin weighted by health score), blocklist check, variant selection (A/B subjects and bodies), spintax resolution, variable replacement, tracking pixel injection, and finally the SMTP send. A single lead's processing touches maybe 6 database queries which isn't great, but at 50 leads per cycle with intentional delays between them, it's never the bottleneck.

Spintax with deterministic output

Most spintax implementations use rand.Intn to pick variants, which means the same template produces different output every time. That's fine for preview, but terrible for debugging. If a user says "the email I sent to john@acme.com looked wrong", I need to be able to reproduce exactly what was sent.

The solution: seed the RNG with an MD5 hash of the lead's email. Same lead always produces same spintax output.

func ParseSpintax(template string, seed string) string {
    // Deterministic random from lead email
    hash := md5.Sum([]byte(seed))
    seedInt := int64(binary.BigEndian.Uint64(hash[:8]))
    rng := rand.New(rand.NewSource(seedInt))

    result := template
    pattern := regexp.MustCompile(`\{([^{}]+)\}`)

    // Resolve innermost braces first (handles nesting)
    for pattern.MatchString(result) {
        result = pattern.ReplaceAllStringFunc(result, func(match string) string {
            inner := match[1 : len(match)-1]
            options := strings.Split(inner, "|")
            return options[rng.Intn(len(options))]
        })
    }
    return result
}

Nested spintax works because we loop until there are no more braces. {Hi|{Hey|Hello}} {{firstName}} resolves the inner {Hey|Hello} first, producing something like {Hi|Hello} {{firstName}}, then resolves the outer one on the next pass. Simple, fast, no recursion.

MCP: letting AI agents control the platform

This was the most fun to build and honestly the reason I'm posting here. We implemented the Model Context Protocol (the thing Anthropic put out for connecting AI agents to tools) as a first class endpoint.

The MCP server sits at POST /api/v1/mcp and accepts JSON-RPC 2.0 requests. You add the server config to Claude or ChatGPT and suddenly you can say things like "pause the Q2 campaign" or "show me today's reply rate" and it works.

type MCPServer struct {
    DB            *gorm.DB
    EncryptionKey string
}

func (s *MCPServer) HandleMCP(c *gin.Context) {
    var req JSONRPCRequest
    c.ShouldBindJSON(&req)
    
    wsID, _ := c.Get("workspace_id")

    switch req.Method {
    case "initialize":
        result = s.handleInitialize()
    case "tools/list":
        result = s.handleToolsList()
    case "tools/call":
        result, rpcErr = s.handleToolCall(req.Params, wsID)
    }
    
    c.JSON(200, JSONRPCResponse{JSONRPC: "2.0", ID: req.ID, Result: result})
}

We expose 8 tools: get_stats, list_campaigns, start/pause_campaign, list_leads, get_inbox, send_reply, get_mailboxes. The tool definitions include JSON Schema input specs so the AI knows what parameters to pass.

What makes this interesting vs a regular REST API: the AI can chain operations. "Check my inbox, find any positive replies from this week, and draft follow-ups" becomes three tool calls the model composes on its own. You'd need a pretty sophisticated frontend to replicate that workflow manually.

Auth works via the same JWT token used for the dashboard. You just add an Authorization header to the MCP config. Each request is scoped to a workspace, so multi-tenant isolation is maintained even when an AI is driving.

Parallel email validation at 100 goroutines

We embedded AfterShip's email-verifier library directly (forked it into our repo because we needed to disable some checks and avoid the dependency on their API). Validation runs as a background task when you upload a CSV.

const validationConcurrency = 100

var verifier = emailverifier.
    NewVerifier().
    DisableSMTPCheck().      // Port 25 blocked on most VPS
    DisableGravatarCheck().  // Too slow for bulk
    EnableDomainSuggest()

func (p *ValidateLeadsProcessor) ProcessTask(ctx context.Context, t *asynq.Task) error {
    // ... load leads ...
    
    sem := make(chan struct{}, validationConcurrency)
    var wg sync.WaitGroup

    for i := range leads {
        lead := leads[i]
        wg.Add(1)
        sem <- struct{}{}  // acquire slot

        go func() {
            defer wg.Done()
            defer func() { <-sem }()  // release

            result, _ := verifier.Verify(lead.Email)
            score, status := mapVerificationResult(result)
            
            p.DB.Model(&models.Lead{}).Where("id = ?", lead.ID).
                Updates(map[string]interface{}{
                    "validation_status": status,
                    "validation_score":  score,
                })
        }()
    }
    wg.Wait()
    return nil
}

100 goroutines might seem aggressive but each one just does a DNS lookup (MX record check) which takes maybe 50-100ms. We benchmarked 500 leads at 3-5 seconds total. The main bottleneck is DNS resolution latency, not CPU or memory.

I should note: we can't do SMTP handshake verification (the "does this mailbox actually exist" check) because basically every cloud VPS provider blocks port 25 outbound. So our validation is really "list hygiene": syntax, disposable domain detection (135K domains in our database), role account filtering, MX record verification, typo suggestion. Not a replacement for MillionVerifier, but catches the obvious junk before you waste sends on it.

Tracking: a 68-byte PNG and some HMAC magic

Open tracking works by embedding a 1x1 transparent PNG in every email. When the recipient's mail client loads it, our server logs the open.

// 68 bytes. Hardcoded because generating it at runtime is silly.
var transparentPixel = []byte{
    0x89, 0x50, 0x4E, 0x47, 0x0D, 0x0A, 0x1A, 0x0A,
    0x00, 0x00, 0x00, 0x0D, 0x49, 0x48, 0x44, 0x52,
    // ... 68 bytes total for a valid PNG
}

func (h *TrackingHandler) TrackOpen(c *gin.Context) {
    trackingID := c.Param("trackingID")
    // Record open, always return the pixel
    c.Data(200, "image/png", transparentPixel)
}

Link tracking rewrites every <a href> in the email body to route through our server. We base64 encode the original URL into the path, so /t/abc123/link/aHR0cHM6Ly... redirects to the original after logging the click.

Unsubscribe links use HMAC-SHA256 tokens with a derived signing key (not the raw encryption key) containing workspace_id:email. When someone clicks unsubscribe, we verify the signature, update the lead status, add them to the workspace blocklist, and show a confirmation page. No database lookup needed to validate the token, it's all in the cryptographic signature.

The warmup system

New domains and mailboxes need to "warm up" before sending at volume. The idea is simple: send a few emails a day, get replies, gradually increase volume over 30 days until the inbox providers trust you.

Our warmup works as a coordinated pool. Each instance registers its mailboxes with a central coordinator, which assigns send/receive pairs across the pool. Instance A sends to Instance B's mailbox, B auto-replies, both get engagement signals. Volume graduates from 2/day on day 1 to 30/day by day 30.

The coordinator is a separate service (running on our infra) because warmup needs a network effect. A single instance warming up against itself looks suspicious to inbox providers. Cross-instance warming with real variety in sending patterns is what makes it work.

Why Go and not Node/Python

Three reasons:

  1. Single binary deployment. Cross compile from my Windows laptop to a Linux amd64 binary, copy it to the server, done. No node_modules, no virtualenvs, no runtime dependencies beyond libc. The API binary is 26MB. The worker is 23MB.
  2. Concurrency is native. The validation worker spawning 100 goroutines to parallelize DNS lookups is trivial. The dispatcher running with context-aware delays between sends is clean. In Node you'd need worker threads or a separate process. In Python, asyncio or multiprocessing, both with their own footguns.
  3. Memory. The API process runs at ~40MB RSS under normal load. The worker at ~60MB. On a 2GB VPS where you also need Postgres, Redis, and the frontend, every MB matters.

GORM is the only part I'm slightly unhappy with. It generates fine SQL for simple queries but the dispatcher's FOR UPDATE SKIP LOCKED requires raw SQL anyway. If I were starting over I might use sqlx or sqlc for the hot paths and GORM only for migrations and simple CRUD.

The middleware stack

Every request goes through: Security Headers -> CORS -> License Guard -> (Auth + Rate Limit for protected routes). The license guard is interesting because it turns the entire API into a brick if the license is invalid:

func LicenseGuardMiddleware(db *gorm.DB) gin.HandlerFunc {
    return func(c *gin.Context) {
        path := c.Request.URL.Path
        
        // Always allow: setup, auth, health, tracking
        if strings.HasPrefix(path, "/api/v1/setup") ||
           strings.HasPrefix(path, "/health") {
            c.Next()
            return
        }

        status := getCachedLicenseStatus(db) // 5-min cache

        switch status {
        case "revoked", "expired", "pending":
            c.AbortWithStatusJSON(403, gin.H{
                "error": "License not active",
            })
            return
        }
        c.Next()
    }
}

Rate limiting is a sliding window implementation per IP (5/min for auth endpoints) and per user (60/min for authenticated API calls). Nothing fancy, just a map of timestamps behind a mutex with a background cleanup goroutine that prunes expired entries every 5 minutes.

Deployment and updates

The whole system ships as a tarball: pre-compiled binaries + a Next.js standalone build + Dockerfiles + docker-compose. The user runs curl | bash to install, which downloads the tarball, builds thin Docker images (just COPY binary into alpine), and starts everything with compose.

Updates happen from the admin dashboard. The API container has Docker socket access, so when you click "Update", it downloads the new tarball, rebuilds images, and runs docker compose up -d --force-recreate. The frontend polls /api/v1/admin/system/version until the new version responds. Yes, the update script restarts the container that's running it. Somehow this works reliably.

What I'd do differently

  • The frontend build situation is annoying. Next.js with output: standalone works great in theory but NEXT_PUBLIC_* env vars baking into the webpack bundle at build time caused us weeks of debugging. If I started over I'd probably use a SPA with Vite and no SSR.
  • GORM for the dispatcher queries was a mistake. Raw SQL for anything touching FOR UPDATE or complex joins. GORM for simple CRUD models and migrations.
  • The warmup coordinator being a separate hosted service means there's a dependency on our infra. Would like to explore a fully P2P approach where instances discover each other, but the anonymity and scheduling complexity makes that non-trivial.
